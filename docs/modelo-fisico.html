As 13 correções — antes e depois

Para cada item: o que o modelo lógico dizia (traduzido literalmente para DDL), o que o banco aceitaria de errado, e o que ficou no modelo físico. Linhas vermelhas são o problema; verdes são o que entrou. Fonte: docs/correcoes-modelo-logico.md.

C1

O tipo timerange não existe no PostgreSQL

fatal
Tabela turma_horario · coluna faixa

Consequência: o PostgreSQL tem tsrange, daterange, int4range… mas nenhum range de time. Um CREATE TABLE literal do modelo morre com type "timerange" does not exist — nada depois disso é criado.

Antes · modelo lógico
CREATE TABLE turma_horario (
  ...
  faixa timerange
);
-- ERROR: type "timerange" does not exist
Depois · modelo físico
CREATE TYPE timerange AS RANGE (subtype = time);

CREATE TABLE turma_horario (
  ...
  faixa timerange NOT NULL
    CHECK (NOT isempty(faixa))
);
Bônus: um range criado assim já ganha o operador && (sobreposição) e suporte a índice GiST — é o que viabiliza a correção C10.
C2

matricula sem unicidade de (aluno, turma)

integridade
Tabela matricula

Consequência: o mesmo aluno se matricula duas vezes na mesma turma — duas linhas, ids diferentes, ambas válidas. Contagem de vagas, histórico e relatórios ficam corrompidos.

Antes
CREATE TABLE matricula (
  id integer PRIMARY KEY,
  aluno_id integer REFERENCES aluno,
  turma_id integer REFERENCES turma,
  data_matricula timestamptz,
  status status_mat_t
);
-- (aluno 7, turma 3) pode entrar N vezes
Depois
CREATE TABLE matricula (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  aluno_id integer NOT NULL REFERENCES aluno (id),
  turma_id integer NOT NULL REFERENCES turma (id),
  data_matricula timestamptz NOT NULL DEFAULT now(),
  status status_mat_t NOT NULL DEFAULT 'confirmada',
  CONSTRAINT uq_matricula_aluno_turma
    UNIQUE (aluno_id, turma_id)
);
Prova: 90_testes_restricoes.sql → OK [C2] matrícula duplicada rejeitada (unique_violation). Efeito colateral útil: a UNIQUE já indexa aluno_id (coluna líder), dispensando um índice extra no Marco 2.
C3

periodo_letivo sem unicidade de (ano, semestre)

integridade
Tabela periodo_letivo

Consequência: dois registros "2026/2" — toda a oferta do semestre poderia se dividir entre períodos duplicados. Também nada impedia semestre 3 ou período que termina antes de começar.

Antes
CREATE TABLE periodo_letivo (
  id smallint PRIMARY KEY,
  ano smallint,
  semestre smallint,
  data_inicio date,
  data_fim date
);
-- (2026, 2) duas vezes? aceita. semestre = 7? aceita.
Depois
CREATE TABLE periodo_letivo (
  id smallint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  ano smallint NOT NULL,
  semestre smallint NOT NULL CHECK (semestre IN (1, 2)),
  data_inicio date NOT NULL,
  data_fim date NOT NULL,
  CONSTRAINT uq_periodo_ano_semestre UNIQUE (ano, semestre),
  CONSTRAINT ck_periodo_datas CHECK (data_inicio < data_fim)
);
Prova: OK [C3] período 2026/2 duplicado rejeitado (unique_violation).
C4

sala sem unicidade de código por campus

integridade
Tabela sala

Consequência: duas salas "T101" no mesmo campus. O código só faz sentido único dentro de um campus — campi diferentes podem (e na carga, repetem) o mesmo código, então a unicidade tem de ser composta, não em codigo sozinho.

Antes
CREATE TABLE sala (
  id integer PRIMARY KEY,
  campus_id smallint REFERENCES campus,
  codigo varchar(10),
  capacidade smallint,
  tipo tipo_sala_t
);
-- 'T101' duas vezes no Asa Sul? aceita.
Depois
CREATE TABLE sala (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  campus_id smallint NOT NULL REFERENCES campus (id),
  codigo varchar(10) NOT NULL,
  capacidade smallint NOT NULL CHECK (capacidade > 0),
  tipo tipo_sala_t NOT NULL DEFAULT 'teorica',
  CONSTRAINT uq_sala_campus_codigo UNIQUE (campus_id, codigo)
);
C5

turma sem unicidade de código por período letivo

integridade
Tabela turma

Consequência: duas turmas "BD2-N1" no mesmo semestre. O código se repete legitimamente entre semestres (a cada nova oferta), mas nunca dentro do mesmo período — de novo, unicidade composta.

Antes
CREATE TABLE turma (
  id integer PRIMARY KEY,
  codigo varchar(15),
  disciplina_id integer REFERENCES disciplina,
  periodo_letivo_id smallint REFERENCES periodo_letivo,
  professor_id integer REFERENCES professor,
  turno turno_t,
  vagas smallint
);
-- 'BD2-N1' duas vezes em 2026/2? aceita. vagas = -5? aceita.
Depois
CREATE TABLE turma (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  codigo varchar(15) NOT NULL,
  disciplina_id integer NOT NULL REFERENCES disciplina (id),
  periodo_letivo_id smallint NOT NULL REFERENCES periodo_letivo (id),
  professor_id integer NOT NULL REFERENCES professor (id),
  turno turno_t NOT NULL,
  vagas smallint NOT NULL CHECK (vagas >= 0),
  CONSTRAINT uq_turma_periodo_codigo
    UNIQUE (periodo_letivo_id, codigo),
  CONSTRAINT uq_turma_id_periodo
    UNIQUE (id, periodo_letivo_id)          -- alvo da FK de C10
);
C6

aluno com curso_id e curriculo_id soltos — currículo de outro curso

integridade
Tabela aluno (+ UNIQUE (id, curso_id) em curriculo)

Consequência: curriculo já pertence a um curso (curriculo.curso_id). Com duas FKs independentes em aluno, um aluno de Computação pode apontar para o currículo de Direito — cada FK é válida isoladamente e o banco aceita. É uma dependência transitiva sem proteção.

Antes
CREATE TABLE aluno (
  ...
  curso_id smallint REFERENCES curso,
  curriculo_id integer REFERENCES curriculo,
  ...
);
Depois
-- em curriculo: superchave-alvo (barata: PK + 1 coluna)
CONSTRAINT uq_curriculo_id_curso UNIQUE (id, curso_id)

-- em aluno:
  curso_id smallint NOT NULL REFERENCES curso (id),
  curriculo_id integer NOT NULL,
  CONSTRAINT fk_aluno_curriculo_do_curso
    FOREIGN KEY (curriculo_id, curso_id)
    REFERENCES curriculo (id, curso_id)
Prova: OK [C6] currículo de outro curso rejeitado (foreign_key_violation composta). Mantivemos as duas colunas do modelo — a correção é amarrá-las, não remover uma.
C7

pre_requisito permite disciplina ser pré-requisito de si mesma

integridade
Tabela pre_requisito

Consequência: a linha (BD2, BD2) é aceita e nenhum aluno consegue cursar BD2 nunca. Limite honesto: ciclos maiores (A→B→A) não são expressáveis em constraint declarativa — a consulta recursiva 5 tem proteção de ciclo e serve de auditoria; trigger é candidata futura.

Antes
CREATE TABLE pre_requisito (
  disciplina_id integer REFERENCES disciplina,
  requisito_id integer REFERENCES disciplina,
  vinculo vinculo_t,
  PRIMARY KEY (disciplina_id, requisito_id)
);
-- (BD2, BD2)? aceita.
Depois
CREATE TABLE pre_requisito (
  disciplina_id integer NOT NULL
    REFERENCES disciplina (id) ON DELETE CASCADE,
  requisito_id  integer NOT NULL
    REFERENCES disciplina (id) ON DELETE CASCADE,
  vinculo vinculo_t NOT NULL DEFAULT 'pre_requisito',
  PRIMARY KEY (disciplina_id, requisito_id),
  CONSTRAINT ck_prereq_nao_reflexivo
    CHECK (disciplina_id <> requisito_id)
);
Prova: OK [C7] pré-requisito reflexivo rejeitado (check_violation).
C8

curriculo sem unicidade de (curso, ano de vigência)

integridade
Tabela curriculo

Consequência: dois "currículo 2026 de CC" distintos, e o aluno pode cair em qualquer um.

Antes
CREATE TABLE curriculo (
  id integer PRIMARY KEY,
  curso_id smallint REFERENCES curso,
  ano_vigencia smallint,
  ativo boolean
);
-- (CC, 2026) duas vezes? aceita.
Depois
CREATE TABLE curriculo (

  ano_vigencia smallint NOT NULL

  CONSTRAINT uq_curriculo_id_curso  UNIQUE (id, curso_id)   -- C6

C9

feriado sem unicidade e sem semântica para campus NULL

integridade
Tabela feriado

Consequência: o mesmo feriado cadastrado N vezes. Definimos: NULL = feriado nacional. Detalhe técnico que pega muita gente: em UNIQUE comum, NULLs não conflitam entre si — dois "7 de setembro" nacionais passariam. O PostgreSQL 15+ resolve com NULLS NOT DISTINCT.

Antes
CREATE TABLE feriado (
  id integer PRIMARY KEY,
  data date,
  descricao varchar(120),
  campus_id smallint REFERENCES campus
);
-- (2026-09-07, NULL) duas vezes? aceita — até com UNIQUE comum.
Depois
CREATE TABLE feriado (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  data date NOT NULL,
  descricao varchar(120) NOT NULL,
  campus_id smallint
    REFERENCES campus (id) ON DELETE CASCADE,  -- NULL = nacional
  CONSTRAINT uq_feriado_campus_data
    UNIQUE NULLS NOT DISTINCT (campus_id, data)
);
Prova: OK [C9] feriado nacional duplicado rejeitado (UNIQUE NULLS NOT DISTINCT).
C10

turma_horario sem proteção contra choque de sala

integridade
Tabela turma_horario (+ UNIQUE (id, periodo_letivo_id) em turma, extensão btree_gist)

Consequência: duas turmas na mesma sala, mesmo dia, faixas sobrepostas. UNIQUE não pega — sobreposição não é igualdade (19:00–20:40 ≠ 19:30–21:10, mas colidem). A resposta é uma restrição de exclusão com GiST, que compara com &&.

Antes
CREATE TABLE turma_horario (
  id integer PRIMARY KEY,
  turma_id integer REFERENCES turma,
  sala_id integer REFERENCES sala,
  dia_semana smallint,
  faixa timerange
);
-- mesma sala, mesmo dia, 19:00–20:40 e 19:30–21:10? aceita.
-- dia_semana = 9? aceita.
Depois
CREATE EXTENSION IF NOT EXISTS btree_gist;
-- (mistura = escalar com && de range no mesmo GiST)

CREATE TABLE turma_horario (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  turma_id integer NOT NULL,
  periodo_letivo_id smallint NOT NULL,   -- denormalização CONTROLADA
  sala_id integer NOT NULL REFERENCES sala (id),
  dia_semana smallint NOT NULL CHECK (dia_semana BETWEEN 1 AND 7),
  faixa timerange NOT NULL CHECK (NOT isempty(faixa)),
  CONSTRAINT fk_horario_turma_periodo
    FOREIGN KEY (turma_id, periodo_letivo_id)
    REFERENCES turma (id, periodo_letivo_id) ON DELETE CASCADE,
  CONSTRAINT ex_sala_sem_choque EXCLUDE USING gist (
    periodo_letivo_id WITH =, sala_id WITH =,
    dia_semana WITH =, faixa WITH &&),
  CONSTRAINT ex_turma_sem_choque EXCLUDE USING gist (
    turma_id WITH =, dia_semana WITH =, faixa WITH &&)
);
Por que periodo_letivo_id entrou aqui: o conflito só existe dentro do mesmo semestre (a sala ocupada na segunda 19h de 2025/2 não conflita com 2026/2). A FK composta garante que a cópia nunca diverge da turma. Prova: OK [C10] choque de sala rejeitado (exclusion_violation via GiST).
C11

log_matricula.matricula_id sem FK — mantido de propósito

decisão
Tabela log_matricula

Decisão: é trilha de auditoria — o registro deve sobreviver à remoção da matrícula que o originou. Com FK + CASCADE o log sumiria junto; com RESTRICT impediria expurgo; com SET NULL perderíamos justamente a referência histórica. Sem FK, com defaults completos. (Testado na prática: um DELETE acidental em matricula apagou o histórico por CASCADE e deixou os 32 mil logs intactos.)

Antes (o modelo já não marcava FK)
CREATE TABLE log_matricula (
  id bigint PRIMARY KEY,
  matricula_id integer,
  acao varchar(20),
  ocorrido_em timestamptz,
  usuario name,
  detalhe jsonb
);
Depois (explicitado + defaults)
CREATE TABLE log_matricula (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  matricula_id integer,            -- SEM FK, de propósito
  acao varchar(20) NOT NULL,
  ocorrido_em timestamptz NOT NULL DEFAULT now(),
  usuario name NOT NULL DEFAULT current_user,
  detalhe jsonb                    -- índice GIN no Marco 2
);
C12

Tipos indicados mas não definidos; nenhuma validação de domínio

omissão
Todas as tabelas · tipos nota_t, pct_t, turno_t, status_mat_t, situacao_t, vinculo_t, tipo_sala_t, tipo_disc_t + novo cpf_t

Consequência: o diagrama cita nota_t, turno_t… mas não diz o que são; sem definição, nota 15, frequência 130%, CPF com letras, turno "tarde" — tudo entra. Também não marca nulidade. Critério adotado: ENUM para conjuntos fechados de rótulos; DOMAIN para faixa/formato sobre tipo base; NOT NULL por padrão.

Antes
nota_a1 nota_t        -- nota_t: ???
frequencia pct_t      -- pct_t: ???
turno turno_t         -- turno_t: ???
cpf char(11)          -- 'ABCDEFGHIJK' aceito
Depois
CREATE DOMAIN nota_t AS numeric(4,2) CHECK (VALUE BETWEEN 0 AND 10);
CREATE DOMAIN pct_t  AS numeric(5,2) CHECK (VALUE BETWEEN 0 AND 100);
CREATE DOMAIN cpf_t  AS char(11)     CHECK (VALUE ~ '^[0-9]{11}$');

CREATE TYPE turno_t      AS ENUM ('matutino','vespertino','noturno');
CREATE TYPE tipo_sala_t  AS ENUM ('teorica','laboratorio','auditorio');
CREATE TYPE vinculo_t    AS ENUM ('pre_requisito','co_requisito');
CREATE TYPE tipo_disc_t  AS ENUM ('obrigatoria','optativa','eletiva');
CREATE TYPE status_mat_t AS ENUM ('pendente','confirmada',
                                  'trancada','cancelada');
CREATE TYPE situacao_t   AS ENUM ('cursando','aprovado','reprovado_nota',
                                  'reprovado_frequencia','trancado');
-- + CHECKs de sanidade: vagas >= 0, capacidade > 0, ch >= 0,
--   nascimento < ingresso, e-mail com '@', grau/titulacao em listas
Prova: OK [C12] nota 11 rejeitada pelo domínio nota_t (check_violation).
C13

Colunas geradas indicadas mas não especificadas

omissão
disciplina.ch_total · historico.media_final

Consequência: o diagrama marca as duas como "gerado" sem dizer a fórmula. Se fossem colunas comuns, alguém gravaria média incoerente com as notas. Sendo GENERATED ALWAYS … STORED, é impossível divergir — e o banco recusa escrita direta. Regra institucional: MF = 0,4·A1 + 0,6·A2; se houver P3, ela substitui a nota que mais beneficia o aluno.

Antes
ch_total smallint      -- "gerado" (como?)
media_final numeric(4,2)  -- "gerado" (como?)
Depois
ch_total smallint GENERATED ALWAYS AS (ch_teorica + ch_pratica) STORED,

media_final numeric(4,2) GENERATED ALWAYS AS (
  CASE
    WHEN nota_a1 IS NULL OR nota_a2 IS NULL THEN NULL
    WHEN nota_p3 IS NULL THEN round(0.4*nota_a1 + 0.6*nota_a2, 2)
    ELSE round(GREATEST(0.4*nota_a1 + 0.6*nota_a2,
                        0.4*nota_p3 + 0.6*nota_a2,
                        0.4*nota_a1 + 0.6*nota_p3), 2)
  END) STORED
Prova: OK [C13] escrita direta em media_final rejeitada (generated_always). No Marco 2, media_final ganhou índice B-tree — indexar a coluna gerada é indexar a regra.

O que não mudamos — e por quê

Convenções do modelo lógico que mantivemos de propósito. Perguntas prováveis na arguição.

PK chamada id em toda tabela

Não é erro: é a convenção mais difundida (Rails, Django, Prisma…). A referência à tabela já vem no nome da FK (campus_id, turma_id), então curso.campus_id → campus.id lê-se sem ambiguidade. Renomear para id_campus divergiria do modelo do professor sem ganho de integridade — e integridade é o que a disciplina avalia.

smallint em campus, curso, período letivo

Tabelas com dezenas de linhas no máximo; smallint (2 bytes) é adequado e o modelo já o indica. Onde há crescimento real — aluno, matricula — é integer; em log_matricula, que só cresce, bigint.

curso_id e curriculo_id ambos em aluno

Redundante, sim — mas o modelo pede as duas colunas. Em vez de remover uma, a correção C6 amarra as duas com FK composta: mantém a conveniência de consulta e elimina a inconsistência.

periodo_letivo_id copiado em turma_horario

Uma denormalização deliberada, exigida pelo EXCLUDE de C10. É controlada: a FK composta impede que a cópia divirja da turma. Denormalizar com proteção é decisão de engenharia; denormalizar sem proteção seria erro.

GENERATED ALWAYS AS IDENTITY em vez de SERIAL

Mesma semântica de autoincremento, mas padrão SQL: impede inserção manual acidental de id, e a sequência pertence à coluna (não sobra órfã em DROP). Não muda o modelo, só a implementação.

Sem índices no DDL

O Marco 1 pede o esquema; índices de desempenho são o Marco 2 (06_indices.sql), com EXPLAIN antes/depois. Os índices que existem no DDL são os que as restrições criam sozinhas (PK, UNIQUE, EXCLUDE).
