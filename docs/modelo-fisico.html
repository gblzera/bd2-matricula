Achados — o que verificamos, o que corrigimos

Para cada item: o que o modelo de partida realmente tem, o que o banco aceitaria de errado, e o que ficou no modelo físico. Linhas vermelhas são o problema; verdes são o que entrou. Fonte: docs/correcoes-modelo-logico.md.

Metodologia — por que confiamos nestas afirmações

Esta análise é medida contra docs/banco_de_dados_matricula_com_erros.sql, o arquivo de partida do professor, e não contra o diagrama do modelo lógico. A diferença é material: o diagrama não expressa CHECK, EXCLUDE nem colunas geradas, e uma leitura só do diagrama sugere ausências que o SQL não tem.

O procedimento foi executável: o arquivo foi carregado num banco descartável em PostgreSQL 17, o catálogo (pg_constraint, information_schema) foi inspecionado para listar o que de fato existe, e cada suposto defeito foi testado por inserção — se o banco aceitou o dado inválido, o defeito é real; se rejeitou, não é.

Resultado de partida: o DDL do professor roda limpo, sem um único erro, e já traz a maior parte das restrições de integridade básicas. Os defeitos reais são mais sutis que ausência de UNIQUE — e são os que interessam.

C15

Tudo em public em vez de um schema próprio

decisão
Correção nossa, não do modelo · sql/01_ddl.sql

Consequência: os dois arquivos do professor abrem com SET search_path TO academico, public. Nossa versão anterior fazia DROP SCHEMA public CASCADE — o que, além de divergir do ponto de partida, derruba junto extensões e quaisquer objetos de terceiros instalados no schema padrão do banco.

Antes · nosso DDL
DROP SCHEMA IF EXISTS public CASCADE;
CREATE SCHEMA public;
CREATE EXTENSION IF NOT EXISTS btree_gist;
-- reset com alcance sobre o schema padrão do banco
-- e desalinhado do material de aula
Depois
DROP SCHEMA IF EXISTS academico CASCADE;
CREATE SCHEMA academico;
SET search_path TO academico, public;

-- extensão em schema estável: `academico` é
-- derrubado a cada execução e a levaria junto
CREATE EXTENSION IF NOT EXISTS btree_gist SCHEMA public;

-- sessões novas já nascem no caminho certo
ALTER DATABASE matricula
  SET search_path TO academico, public;
Schema estável para infraestrutura, schema próprio para os dados. A função aluno_id_de(), que é SECURITY DEFINER, teve o SET search_path migrado junto — se tivesse ficado apontando para public, o RLS quebraria em silêncio.
E1

O trigger fn_valida_vaga() não protege a última vaga

concorrência
Modelo de partida · linhas 194–218

Consequência: check-then-act clássico. Entre o count(*) e a gravação não há nada que impeça outra sessão de fazer o mesmo. Em Read Committed — o isolamento padrão — duas sessões leem a mesma contagem, ambas passam no IF, e a turma fecha com mais matrículas do que vagas. Um trigger BEFORE INSERT não é mecanismo de exclusão mútua: ele dá a aparência de proteção, o que é pior do que não ter proteção nenhuma.

Antes · modelo de partida
CREATE FUNCTION fn_valida_vaga() RETURNS trigger AS $$
  SELECT vagas INTO v_vagas FROM turma
   WHERE id = NEW.turma_id;
  SELECT count(*) INTO v_ocupadas FROM matricula
   WHERE turma_id = NEW.turma_id ...;
  IF v_ocupadas >= v_vagas THEN RAISE EXCEPTION ...
$$;
-- 2 sessões, 1 vaga -> ambas passam -> 9/8
Depois · duas correções
-- A (adotada): bloqueio explícito
SELECT vagas INTO v_vagas FROM turma
 WHERE id = p_turma FOR UPDATE;

-- B (documentada): nível de isolamento
BEGIN ISOLATION LEVEL SERIALIZABLE;
-- SSI aborta uma com SQLSTATE 40001
-- e a aplicação retenta
É o erro mais importante do modelo — e é deliberado: o enunciado pede exatamente que a anomalia seja reproduzida e corrigida de dois modos. Implementação em sql/07_transacoes.sql; execução real em duas sessões capturada em docs/evidencias/transacoes-demo.md.
C10

A restrição de exclusão de sala é forte demais, não fraca

integridade
Tabela turma_horario · modelo de partida, linhas 138–140

O modelo já protege contra choque de sala — mas a restrição não inclui o período letivo. Consequência: uma sala ocupada na segunda das 08:15 às 11:00 em 2026/2 fica bloqueada naquele horário para sempre, em todos os semestres seguintes. O modelo não falha em impedir o choque; ele impede reuso legítimo.

Antes · modelo de partida
ALTER TABLE turma_horario ADD CONSTRAINT ex_sala_ocupada
  EXCLUDE USING gist (
    sala_id    WITH =,
    dia_semana WITH =,
    faixa      WITH &&
    -- falta o período letivo
  );
-- JB1, segunda 08:15 em 2026/1 é REJEITADA
-- porque 2026/2 já usa o mesmo horário
Depois · modelo físico
ALTER TABLE turma_horario ADD CONSTRAINT ex_sala_sem_choque
  EXCLUDE USING gist (
    periodo_letivo_id WITH =,
    sala_id    WITH =,
    dia_semana WITH =,
    faixa      WITH &&
  );
-- denormalização controlada: o período entra em
-- turma_horario amarrado por FK composta
FOREIGN KEY (turma_id, periodo_letivo_id)
  REFERENCES turma (id, periodo_letivo_id)
Verificado por inserção: horário idêntico em turma de outro período letivo é rejeitado com conflicting key value violates exclusion constraint "ex_sala_ocupada". A denormalização viola a 3FN de propósito — e o risco que a 3FN previne (a cópia divergir) é fechado pela FK composta. Acrescentamos ainda EXCLUDE (turma_id, dia_semana, faixa): a própria turma não pode ter dois horários sobrepostos.
C6

aluno com curso_id e curriculo_id soltos — currículo de outro curso

integridade
Tabela aluno (+ UNIQUE (id, curso_id) em curriculo)

Consequência: curriculo já pertence a um curso (curriculo.curso_id). Com duas FKs independentes em aluno, um aluno de Computação pode apontar para o currículo de Direito — cada FK é válida isoladamente e o banco aceita. É uma dependência transitiva sem proteção.

Antes
CREATE TABLE aluno (
  ...
  curso_id smallint REFERENCES curso,
  curriculo_id integer REFERENCES curriculo,
  ...
);
Depois
-- em curriculo: superchave-alvo (barata: PK + 1 coluna)
CONSTRAINT uq_curriculo_id_curso UNIQUE (id, curso_id)

-- em aluno:
  curso_id smallint NOT NULL REFERENCES curso (id),
  curriculo_id integer NOT NULL,
  CONSTRAINT fk_aluno_curriculo_do_curso
    FOREIGN KEY (curriculo_id, curso_id)
    REFERENCES curriculo (id, curso_id)
Prova: OK [C6] currículo de outro curso rejeitado (foreign_key_violation composta). Mantivemos as duas colunas do modelo — a correção é amarrá-las, não remover uma.
C9

feriado: a unicidade existe, mas o NULL a fura

integridade
Tabela feriado · modelo de partida, linha 114

Consequência: o modelo tem UNIQUE (data, campus_id), mas campus_id é anulável e dois NULLs nunca conflitam entre si num UNIQUE comum. Com a convenção “NULL = feriado nacional”, todo feriado nacional é infinitamente duplicável.

Antes · modelo de partida
campus_id smallint REFERENCES campus,  -- NULL = todos
UNIQUE (data, campus_id)

-- ('2026-09-07','Independência',NULL)
-- ('2026-09-07','Duplicata',    NULL)  ← ACEITO
Depois · modelo físico
campus_id smallint REFERENCES campus (id),
CONSTRAINT uq_feriado
  UNIQUE NULLS NOT DISTINCT (campus_id, data)
-- recurso do PostgreSQL 15+: NULLs conflitam
-- COMMENT documenta: NULL = feriado nacional
Verificado por inserção no modelo de partida: a duplicata nacional foi aceita e a tabela ficou com 2 linhas para 07/09. Prova da correção: OK [C9] feriado nacional duplicado rejeitado (UNIQUE NULLS NOT DISTINCT).
C13

A fórmula da média pode punir quem faz a P3

integridade
Tabela historico · coluna media_final · modelo de partida, linhas 174–181

Consequência: o modelo já traz a coluna gerada com fórmula — mas o GREATEST tem só dois termos e falta o terceiro, 0.4·a1 + 0.6·a2 (a média sem P3). Um aluno que já passaria com A1 e A2, fizer a P3 e for mal, termina com média menor do que teria sem prestá-la. A P3 é substitutiva: nunca deveria piorar o resultado.

Antes · modelo de partida
media_final numeric(4,2) GENERATED ALWAYS AS (
  CASE
    WHEN nota_a1 IS NULL OR nota_a2 IS NULL THEN NULL
    WHEN nota_p3 IS NULL THEN round(0.4*a1 + 0.6*a2, 2)
    ELSE round(greatest(0.4*p3 + 0.6*a2,
                        0.4*a1 + 0.6*p3), 2)
  END) STORED
-- a1=8 a2=8 (MF 8,0); faz P3=2 -> MF cai para 5,6
Depois · modelo físico
media_final numeric(4,2) GENERATED ALWAYS AS (
  CASE
    WHEN nota_a1 IS NULL OR nota_a2 IS NULL THEN NULL
    WHEN nota_p3 IS NULL THEN round(0.4*a1 + 0.6*a2, 2)
    ELSE round(GREATEST(0.4*a1 + 0.6*a2,
                        0.4*p3 + 0.6*a2,
                        0.4*a1 + 0.6*p3), 2)
  END) STORED
-- a P3 só pode melhorar
Por ser GENERATED ALWAYS … STORED, é impossível existir média inconsistente com as notas: a regra é do banco, não da aplicação. Prova: OK [C13] escrita direta em media_final rejeitada (generated_always). STORED é a única modalidade no PG 17 — e é o que torna a coluna indexável (índice B-tree do Marco 2, ganho de 46×).
C5

A unicidade de turma é mais fraca do que parece

integridade
Tabela turma · modelo de partida, linha 125

desempenho

C11

log_matricula.matricula_id sem FK — mantido de propósito

decisão
Tabela log_matricula

Decisão: é trilha de auditoria — o registro deve sobreviver à remoção da matrícula que o originou. Com FK + CASCADE o log sumiria junto; com RESTRICT impediria expurgo; com SET NULL perderíamos justamente a referência histórica. Sem FK, com defaults completos. (Testado na prática: um DELETE acidental em matricula apagou o histórico por CASCADE e deixou os 32 mil logs intactos.)

Antes (o modelo já não marcava FK)
CREATE TABLE log_matricula (
  id bigint PRIMARY KEY,
  matricula_id integer,
  acao varchar(20),
  ocorrido_em timestamptz,
  usuario name,
  detalhe jsonb
);
Depois (explicitado + defaults)
CREATE TABLE log_matricula (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  matricula_id integer,            -- SEM FK, de propósito
  acao varchar(20) NOT NULL,
  ocorrido_em timestamptz NOT NULL DEFAULT now(),
  usuario name NOT NULL DEFAULT current_user,
  detalhe jsonb                    -- índice GIN no Marco 2
);

C14

Nomenclatura de chaves — padronização deliberada

decisão
Todas as tabelas · pendente de execução

O modelo do professor usa id como PK e <tabela>_id como FK. Isso é uma convenção coerente — não um erro: curso.campus_id → campus.id lê-se sem ambiguidade. Nossa mudança é padronização deliberada, e o argumento honesto é este, não “o modelo estava errado”.

Convenção do modelo
campus (id, nome, cidade)
curso  (id, codigo, ..., campus_id)

SELECT * FROM curso c
  JOIN campus ca ON ca.id = c.campus_id;
Convenção adotada
campus (id_campus, nome, cidade)
curso  (id_curso, codigo, ..., id_campus)

SELECT * FROM curso
  JOIN campus USING (id_campus);
Ganho concreto: a FK recebe o mesmo nome da PK que referencia, habilitando JOIN … USING e tornando o nome autoexplicativo em consultas com muitas junções. Onde a mesma tabela é referenciada por papel, o nome carrega o papel — pre_requisito.id_disciplina + pre_requisito.id_requisito.

O que não mudamos — e por quê

Convenções do modelo de partida que mantivemos de propósito. Perguntas prováveis na arguição.

O trigger fn_valida_vaga() continua existindo

Não removemos o trigger do modelo, apesar de E1 mostrar que ele não protege sob concorrência. Ele segue útil como rede de sanidade para gravações fora da transação de matrícula: barra o caso sequencial óbvio. O que mudou é o entendimento do papel dele — proteção de verdade vem do bloqueio explícito ou do nível de isolamento, nunca do trigger sozinho.

smallint em campus, curso, período letivo

Tabelas com dezenas de linhas no máximo; smallint (2 bytes) é adequado e o modelo já o indica. Onde há crescimento real — aluno, matricula — é integer; em log_matricula, que só cresce, bigint.

curso_id e curriculo_id ambos em aluno

Redundante, sim — mas o modelo de partida traz as duas colunas e removê-las mudaria a interface esperada. Em vez disso, a correção C6 amarra as duas com FK composta: mantém a conveniência de consulta e elimina a inconsistência.

periodo_letivo_id copiado em turma_horario

Uma denormalização deliberada, exigida pelo EXCLUDE de C10. É controlada: a FK composta impede que a cópia divirja da turma. Denormalizar com proteção é decisão de engenharia; denormalizar sem proteção seria erro.

GENERATED ALWAYS AS IDENTITY em vez de SERIAL

Mesma semântica de autoincremento, mas padrão SQL: impede inserção manual acidental de id, e a sequência pertence à coluna (não sobra órfã em DROP). Não muda o modelo, só a implementação.

Sem índices no DDL

O Marco 1 pede o esquema; índices de desempenho são o Marco 2 (06_indices.sql), com EXPLAIN antes/depois. Os índices que existem no DDL são os que as restrições criam sozinhas (PK, UNIQUE, EXCLUDE).
